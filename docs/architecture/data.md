# Data

## SQLite, on disk

One file, opened through `better-sqlite3`, with two pragmas set on every
connection:

```ts
db.pragma("journal_mode = WAL"); // a read during a write does not block
db.pragma("foreign_keys = ON"); // SQLite otherwise ignores every REFERENCES
```

`foreign_keys = ON` is not optional politeness — without it SQLite silently
ignores every `REFERENCES` clause in the schema, and the constraints in the
migrations would be decoration.

**The database is not one file.** Write-ahead logging means recent transactions
live in `oikonomia.db-wal` until a checkpoint folds them back, with
`oikonomia.db-shm` alongside. Anything that moves, copies or backs up the
database must treat the three as a set — see
[deployment](deployment.md#restoring).

Location comes from `OIKONOMIA_DB`. In development it defaults to
`.data/oikonomia.db` under the working directory; a production process refuses
to guess, because the application directory is replaced on redeploy and a
database inside it would go with it.

## Migrations

A migration is a `.sql` file in `src/server/db/migrations/`, named
`NNN_description.sql`. There are **35**. They run in numeric order, exactly
once each, inside a transaction, and are recorded in `schema_migrations`.

A uniqueness rule must not rely on a nullable column: SQL treats NULLs as
distinct, so `UNIQUE (a, b)` with `b` NULL never matches and an `ON CONFLICT`
upsert silently becomes an insert. `configuration_setting` did exactly that
until 034 keyed it on `IFNULL(option_id, '')` and `IFNULL(field, '')` with an
expression index, which the repository's upsert names as its conflict target.

Ordering is by the numeric prefix, never by filename sort or modification time,
and two migrations claiming the same version is an error — which is exactly
what versioning exists to prevent.

**There is deliberately no "down".** Rolling a schema backwards is a production
discipline this has not earned, and a half-written `down` is worse than none.
Restoring from a backup is the recovery path.

### Migrations are carried inside the build

```ts
const SOURCES = import.meta.glob("./migrations/*.sql", {
  query: "?raw",
  import: "default",
  eager: true,
});
```

They used to be read from disk at runtime with `readdirSync`. That works in the
repository, where the SQL sits beside the module, and fails completely in a
production build: the bundler has no reason to know that a directory read at
runtime refers to files it should copy.

The symptom was not a missing-migration error. Every page of a deployed
installation showed _"Oikonomia could not be reached"_, because opening the
database is the first thing a request does. `import.meta.glob` states the
dependency at build time so the SQL cannot be left behind, and
`bundled-migrations.test.ts` fails if it ever is — version for version, name
for name, SQL for SQL.

`npm run smoke` starts the built server against an empty file and insists the
schema appears, because that is the failure no unit test can see.

### No migration inserts business data

Migration 032 creates an account for every existing person **without a
credential**, deliberately: a migration that issued passwords would be the hole
that work existed to close. On an empty installation it creates none.

## What every record has

Two things, and no more:

```ts
newId("rep"); // "rep-9f3c…" — prefixed, random, generated by the application
nowIso(); // ISO 8601 UTC
```

An id says what it identifies, so a log line, a URL and a foreign key are all
readable, and a note id pasted into a report lookup fails loudly instead of
quietly finding nothing. Ids are random rather than sequential because two
processes must never be able to agree on the same next number.

Everything else about a record — which columns it has, what its status means —
belongs to the domain that owns it. This is deliberately not the start of a
generic repository framework.

## Dates and timestamps

**Timestamps are ISO 8601 in UTC. Domain dates stay `yyyy-MM-dd`.**

The distinction matters more than it looks. A gathering on `2026-09-12`
happened on the twelfth wherever anybody reads about it; it is not an instant
that moves across the date line.

```text
                      fromISO (parseISO)    new Date()
America/Toronto       12 Sep                11 Sep   ← off by one
Pacific/Midway        12 Sep                11 Sep   ← off by one
Pacific/Kiritimati    12 Sep                12 Sep
```

`fromISO` is date-fns `parseISO`, which reads a date-only string as **local**
midnight. `new Date` reads it as UTC and renders the day before for everybody
west of Greenwich. The two look interchangeable, and swapping them would
quietly move every date in the binder — so
`dates-across-timezones.test.ts` runs five zones from UTC-11 to UTC+14 plus
four daylight-saving boundaries.

## Concurrency

Records that two leaders might write at once carry a `version`. A save sends
the version it read; the service refuses if the stored version has moved on:

```
ApiError.conflict(…)   →   409
```

The second writer is **told**, rather than silently winning or silently losing.
Verified with two browsers on one meeting note: the stale save was refused, the
database kept the first writer's text, and the second saw _"This note was
changed somewhere else while you were writing. Reopen it to see the current
version."_ — with their own text still on screen to copy first.

## SQL

Every statement is prepared with bound parameters. No query anywhere in
`src/server/repositories/` is assembled by string concatenation, which is why
SQL injection is not a reachable vector rather than merely a guarded one.

Repositories hold SQL and nothing else — no authorization, no domain rules. A
repository that decided who may read something would be a second, quieter copy
of the access rules.

## Deactivate is not delete

People, ministries, campuses and vocabulary entries are made unavailable for
new records while everything that already refers to them keeps working. A
record is not orphaned to tidy a list, and history stays readable. The same
principle governs assignment status: `ended` is kept.

## Artifacts

Exports, packages and backups are written through a storage provider rather
than straight to the filesystem, because the destination is the part of this
domain most likely to change. References handed out are opaque ids, never
paths — a path in a response is a way to ask for another one — and the store
refuses any reference that resolves outside its root.

Artifact references use `randomBytes`, not `Math.random()`: two exports
requested in the same millisecond must not be able to collide, and a guessable
reference is one somebody can ask for.

## Encrypted backups

Off unless `OIKONOMIA_BACKUP_KEY` is set. With it, every backup file — in the
artifact directory and in `OIKONOMIA_BACKUP_DIR` — is encrypted with
AES-256-GCM and ends in `.db.enc`. Without it, a backup is the SQLite file
itself, exactly as it has always been.

The key is 32 random bytes, written as 64 hex characters or as base64:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"
```

A key that is set but is not 32 bytes does **not** fall back to plain backups:
every backup fails, and the Continuity panel says why, until it is corrected.
Quietly writing unencrypted copies would leave somebody believing theirs are
encrypted.

### The file

A 36-byte header — `OIKOBAK`, a format version, the 12-byte IV and the 16-byte
authentication tag — then the ciphertext of the database. The header is
authenticated along with the body, so an altered file is refused, not opened.
The job records `format` as `sqlite+aes-256-gcm` or `sqlite`, and its checksum
is of the stored (encrypted) file, so a copy can be checked without the key.

Encryption is recognised from the file, not from today's setting. Verifying a
backup decrypts it beside the installation with the server's key; a missing or
wrong key fails the verification with that reason. A wrong key and a damaged
file look the same to GCM, and the message says so rather than guessing.

### Key custody

- **Without the key, an encrypted backup cannot be restored.** Not by
  Oikonomia, not by anybody. Losing the key loses every backup taken with it.
- **Keep the key away from the backups.** A key stored beside the files it
  protects protects nothing. Keep it in the installation's private settings
  file and, separately, somewhere the people responsible for the church's
  records can reach if this server is gone — a password manager or a sealed
  paper copy, not the backup volume.
- **The key never leaves the server's settings.** The panel says whether
  backups are encrypted, never the key; the process taking the copy receives
  it over a private channel, not in its arguments or environment.
- **Restoring** uses `scripts/ops/decrypt-backup.mjs`, which reads the key
  from the environment — see Restoring in [deployment.md](deployment.md#restoring).

### Rotating the key

Set the new key and restart. New backups use it; existing backups stay
encrypted with the key they were taken with, and nothing re-encrypts them.

So **keep the old key for as long as any backup taken with it is kept** —
until retention has removed the last of them. Record which key was in use from
when, because a backup's file does not name its key. Verifying an old backup
under the new key fails with the wrong-key reason; that is expected, not
damage.

Turning encryption off (unsetting the key) works the same way: new backups are
plain, and the old key is still needed for the encrypted ones.
